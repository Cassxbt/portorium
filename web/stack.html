Under the hood

Which model or engine runs each step, and which steps are not a model.

Retrieval uses two Nemotron models; three roles call Nemotron 3 Ultra; Zetaris answers three questions; memory is Meterless H-MEM. The decision is plain code you can read in one screen.

Zetaris

One virtual layer for the schedule and the precedents

The USL portorium holds hts_line and hts_code (HTS 2026 Rev 21), ruling and ruling_code (CBP rulings and the codes they cite), and hts_release, a REST table that reads the live USITC release. A second USL, audit, holds the verdict log.

Liveness is a data-quality decision

code_in_schedule fails a ruling code that is not a line of the current schedule; parent_survives fails one whose 8-digit parent is gone too, which separates a split from a removal. At start-up Portorium cross-checks its liveness sets against each rule's own invalid records and refuses to start if they differ.

Across 75,870 ruling codes: 53,723 living, 7,938 split, 14,209 removed.

A code's current wording, read from the schedule's structure

The schedule keeps its hierarchy as indentation. One Zetaris query over the loaded release walks it: for a 10-digit code, each level above it, keeping an ancestor only if it comes after every ancestor above it (heading, subheading, statistical groups) and every other line at each level. The Critic reads that, so "Other" means what the schedule says it means today.

Every verdict goes back in

Live verdicts are inserted into audit.verdict_log. classified_code_living flags a classified verdict whose code has since left the schedule; release_is_snapshot flags when USITC publishes a release newer than the one loaded.

Meterless

Nightshift routes every reasoning call

Portorium talks to Nightshift's OpenAI-compatible endpoint on the Mac. Every answer carries a receipt with routed_model and receipt_id; the verdict keeps it and the trace logs it, so each Nemotron call is attributable. For the evaluation, Nightshift's answer cache is set to 0% and each request carries a run tag, so no answer is replayed from an earlier run.

H-MEM is the memory engine

A Python port of the Meterless H-MEM reference (Apache-2.0). It passes the 13 official conformance vectors, and a mutation test shows the vectors catch a broken port. Broker sign-offs and importer answers are long-term factual memories with provenance; a wipe is logged in H-MEM's ledger.

NVIDIA Nemotron

Four models, each with one job

  • Nemotron 3.5 Embed 1B: one vector per ruling subject, 56,371 rulings.
  • Nemotron 3.5 Rerank 8B: orders the 20 nearest rulings for each product.
  • Nemotron 3 Ultra 550B-A55B: three roles. The Adjudicator compares precedents, the Proposer picks a cited code, the Critic checks it against the schedule's wording.
  • Nemotron 3.5 Lightning 30B-A3B: evaluation baseline only.

Why Embed and Rerank are called directly

The Nightshift M1–M4 build returns 501 route_not_implemented for /v1/embeddings, so retrieval calls NVIDIA's API with the same key. Every reasoning call goes through Nightshift.

What is different about this use
A model suggests; it never decides.

The Proposer may only pick a code a retrieved ruling cites. Zetaris and the Critic verify it; plain rules decide.

Zetaris decides what is alive.

Two registered rules define what is alive. Each request runs a query that mirrors them, the gate's view is checked against the rules' own invalid records at start-up, and the ledger's rules re-check past verdicts.

Memory is judged, not trusted.

A broker's remembered decision is weighed by the model like any precedent, and dropped if its code has died.
